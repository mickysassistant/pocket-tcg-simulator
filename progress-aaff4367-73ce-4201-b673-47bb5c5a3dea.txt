## Codebase Patterns
- Project uses plain JavaScript (no TypeScript)
- Tests use custom test runner with manual assertions and run with `node tests/*.test.js`
- Main entry point is src/index.js which exports createGame and game systems
- Game systems: GameState, TurnManager, DrawSystem, EnergySystem, EvolutionSystem, SupporterSystem, DeckManager, WinCondition
- Tests use assert.strictEqual and other manual assertions
- Project uses Puppeteer for E2E smoke tests
- CLI commands are in src/cli/commands/*.js, each exporting a handler function
- CLI services are in src/cli/services/*.js for shared functionality
- All CLI commands support --json output via argv.formatOutput()
- All CLI errors include stable reason codes (e.g., MISSING_ARGUMENT, UNKNOWN_SUBCOMMAND)
- Config stored in ~/.tcgp/config.json (respects XDG_CONFIG_HOME if set)
- Database stored in ~/.local/share/tcgp/tcgp.db (respects XDG_DATA_HOME if set)
- node:sqlite uses DatabaseSync (synchronous API), not Database
- Tests use XDG_DATA_HOME environment variable for isolated test databases
- Module cache clearing with delete require.cache[require.resolve(...)] between tests
- Foreign key constraints in SQLite: parent records must exist before child records
- UNIQUE constraint errors from SQLite should be caught and mapped to app-specific error codes
- Global CLI parser should pass through unknown `--flags` to command positional args so subcommands can parse their own options
- CLI action contracts are centralized in `src/cli/services/actions.js` with a schema-per-action registry and shared validator returning stable reason codes (`VALIDATION_ERROR`, `UNKNOWN_ACTION`, etc.)
- Determinism is achieved via SeededRNG class (Mulberry32 algorithm) and CoinQueue class for controlled randomness
- Game determinism: pass seed and/or coinQueue to createGame(); GameState and DeckManager use seeded RNG for all random operations
- Session metadata stores determinism configuration (seed and coinQueue) for persistence and reproducibility
- Snapshots are stored as independent state copies with labels; they include full state data (turn number, phase, current player, players object) for checkpoint/restoration workflows
- Replay files export session events with metadata; replay runner reconstructs game with mock decks and executes action events in sequence; state comparison is informational by default but can be strict with --compare flag
- Rule-check style commands follow a two-layer validation pattern: action schema validation first, then stateful business-rule validation with explanatory messages
